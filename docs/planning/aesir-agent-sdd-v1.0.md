# 第一部分　项目章程（Constitution）

> 来源文件：`.specify/memory/constitution.md`

## Aesir Agent 服务 Constitution

> 本文件是本项目的**最高约束**。任何规格（spec）、计划（plan）、任务（tasks）与代码变更
> 都必须通过本文件的合规检查；与本文冲突的设计一律不采纳。

### Core Principles

#### I. 配置外置，代码不写业务数值（Configuration Over Code）

人格文案、能力目录、阈值、优先级、行为节流参数、好感度规则、表现 ID 白名单，
**一律外置为版本化配置文件**（YAML／JSON），代码中不得硬编码业务数值或角色台词。

- 调参只改配置，不改代码；配置结构非法时**快速失败**并给出可读错误（文件 + 字段路径）。
- 配置文件是版本库资产，享受与代码同等的评审与版本管理。
- 每个配置块携带版本标识（如 `profile_version`、`revision`），并在响应中回带，便于归因。

理由：本项目的人格与平衡性需要大量试玩调参，硬编码会让每次调整都变成代码变更与回归风险。

#### II. 模型输出不可信（Untrusted Model Output, NON-NEGOTIABLE）

任何来自大模型或外部输入的内容，**必须经过三重校验**才能影响游戏：

1. **结构校验**：严格 Schema，多余字段一律拒绝（`extra=forbid`）。
2. **白名单校验**：只能引用本次上下文中出现过的稳定 ID；白名单外 ID 一律拒绝，**不得静默替换**。
3. **人设一致性校验**：输出文本不得出现出戏术语、不得违反角色禁忌表达、不得宣称不存在的事实。

任一层失败 → 降级（重试一次 → 规则回退 → 安全候选 → 明确拒绝），并在 `source` 字段留下痕迹。
**绝不把"模型说可以"当作可以。**

理由：模型是概率系统，而游戏状态是确定性的；让它直接决定数值或绕过校验会导致不可复现的破坏。

#### III. UE 是唯一权威端（Single Source of Truth: UE）

血量、伤害、位移、物品、技能合法性、可达性、动画表现——**全部由 UE 计算与裁定**。
服务只输出**受限的候选指令**，UE 必须拥有最终否决权。

- 服务不得假设快照之后世界仍然如此；不得修改快照后当作权威状态回写。
- 任何改变游戏世界的操作必须走指令通道，服务内部工具**只读**。
- 即使服务声明"可执行"，UE 仍须二次校验目标、距离、资源、冷却、状态、可达性。

理由：跨进程状态一致性无法靠约定保证，只能靠单向权威 + 二次校验。

#### IV. 测试先行（Test-First, NON-NEGOTIABLE）

功能实现前必须先有可失败的测试；无测试的功能视为未完成。

- 每个新能力至少覆盖四类用例：**正常、不可识别、条件不满足、重复事件**。
- 契约变更必须先更新文档与 golden 样例，再改两端代码。
- 全量测试必须保持绿色；外部依赖缺失时相关用例**自动跳过**而非失败。
- 测试必须隔离外部后端（默认使用规则与模拟后端），不得依赖网络。

理由：本项目是"可解释的确定性策略 + 概率性表达"，没有测试就无法证明策略未被改坏。

#### V. 可解释与可回退（Explainability & Graceful Degradation）

每一次决策都必须能回答"为什么"，且每一个环节都必须能安全失败。

- 响应必须携带决策原因码、来源标记与策略版本号。
- 任一子系统（模型、语音、记忆、关系数值、工具、配置）故障时，服务仍须可用，且功能降级而非报错。
- 服务不可用时，客户端必须有本地兜底，**不得阻塞游戏主流程**。
- 禁止在无依据时编造事实；不确定就明确承认不确定。

理由：答辩与调试都依赖"逐条解释";同时课程项目的演示环境不可控，健壮性决定能否讲完。

#### VI. 单一命令寻址（Single Command Addressing）

系统只存在**一套下发命令体系**：一个统一信封 + 按动作类型判别的联合类型。

- 禁止为不同活动场景新起平行的协议族或端点命名空间。
- 实现层按活动域**分文件**放入同一目录，保证可读性与可扩展性；新增动作类型不改动其他域文件。
- 客户端侧同理：一个结构体 + 按类型分发，不按域拆多套结构。

理由：历史上"两套寻址"是协议漂移与联调事故的主要来源；分文件而非分体系，兼顾秩序与可读。

#### VII. 简单优先（Simplicity / YAGNI）

- 不引入数据库、消息队列、向量库等重型依赖，除非有明确且可验证的必要性。
- 不做投机性抽象（为"将来可能的 N 个场景"提前设计的机制，需在本文档中论证）。
- 首版只交付能被演示与验收的能力；可选加分项排在主线之后。
- 复杂度必须被论证：任何"必要的复杂"都要在计划文档中写明理由。

理由：课程项目的时间预算是第一约束；可讲清楚的简单系统优于讲不清楚的复杂系统。

### 技术约束（Technology & Compliance Constraints）

#### 运行与部署

- 服务为**本机单机部署**，仅监听回环地址；禁止绑定公网接口。
- 不依赖外部中间件；持久化采用本地文件。运行环境与依赖版本在计划文档中固定。
- 一键可启动、可测试、可在无外网环境下以规则链路完整运行。

#### 安全与隐私

- 凭据仅存放于被版本控制忽略的本地环境文件，禁止进入代码、文档、日志与响应。
- 不采集、不存储原始音频；玩家原始输入可按配置不落盘（默认仅保留摘要）。
- 输出不得包含内部路径、资产名、坐标、函数名等实现细节。
- 外部输入进入模型上下文前必须做隔离与转义，防止指令注入覆盖系统人格。

#### 表现与合规内容

- 角色表达禁止占有、控制、贬低、胁迫与情感勒索式内容；该约束属于**功能需求**而非风格建议，须自动校验。
- 涉及身份、未成年人、暴力与不当内容的表达一律拒绝生成。

### 开发工作流与质量门（Development Workflow & Quality Gates）

1. **规格先行**：先写规格（本目录 `specs/`），明确用户价值与可测量成功标准，再进入计划与实现。
2. **计划一致**：计划文档必须逐条回引规格编号，出现偏离须显式说明理由。
3. **任务可验收**：任务分解必须颗粒到"可独立完成并可验证"，并标注依赖与并行可能。
4. **契约变更纪律**：文档与 golden 样例先改，再改实现；破坏性变更必须提升协议版本号。
5. **质量门**：全量测试绿色 + 规格质量清单通过 + 合规检查（本文件"技术约束"逐条）通过，方可视为完成。
6. **可观测**：所有对外响应包含请求关联标识、来源标记、原因码与策略版本。

### Governance

- 本文件**凌驾于其他一切实践与约定**之上；冲突时以本文件为准。
- 修订需说明动机、影响范围与迁移方案，并同步更新版本号与修订日期。
- 每次评审须逐条核验本文件合规性；无法判定合规时默认**保守方案**（拒绝执行 + 说明原因）。
- 运行期的具体开发指引以本文件为纲，细节约定记录在项目既有文档体系中。

### User Scenarios & Testing *(mandatory)*

> 说明：以下故事按重要性排序，每个故事都是**可独立开发、独立测试、独立演示**的功能切片。
> P1 故事构成最小可交付闭环；P2 为完整体验所必需；P3 为架构与扩展性目标。

#### User Story 1 - NPC 记得我，也记得我们一起经历的事 (Priority: P1)

玩家与 NPC 相处时，NPC 能接续上次的话题、记得玩家的偏好与共同经历（例如一起击败过某个强敌、玩家曾替她挡下攻击、玩家答应过她某件事）。玩家重启游戏后再次对话，NPC 的记忆与关系状态仍然存在，不会表现得像初次见面。

**Why this priority**: 这是"人格塑造"与"聊天机器人"的分界线。没有长期记忆，NPC 只是一个无状态应答器，本项目的核心卖点不成立。

**Independent Test**: 与 NPC 完成一段包含特定信息（如玩家说过"我怕高"）的对话 → 完整重启游戏与服务 → 再次对话并询问相关内容 → 验证 NPC 能自然引用该信息。单独交付此故事即可演示"她记得我"。

**Acceptance Scenarios**:

1. **Given** 玩家首次与 NPC 对话并告知个人偏好，**When** 玩家结束会话并重新进入游戏，**Then** NPC 在后续对话中能自然地体现对该偏好的记忆，而非重新询问。
2. **Given** 玩家与 NPC 共同完成一次有意义的战斗，**When** 玩家在战后谈及该战斗，**Then** NPC 能引用这次共同经历的具体细节，而非泛泛回应。
3. **Given** 玩家向 NPC 作出承诺（如"我会替你找回那本笔记"）或 NPC 向玩家作出承诺，**When** 后续任意时间再次对话，**Then** 该承诺在 NPC 的言行中持续存在，直到被兑现或明确解除。
4. **Given** 记忆内容已达到配置容量上限，**When** 产生新的重要经历，**Then** 系统按重要性优先保留重要内容，淘汰低价值旧内容，且最核心的记忆（承诺、重大事件）不被淘汰。
5. **Given** 玩家希望重新开始，**When** 执行记忆重置，**Then** NPC 回到初始人格状态，不残留任何旧记忆。
6. **Given** 记忆存储暂时不可用，**When** 玩家继续对话，**Then** NPC 仍能正常回应（仅表现为不记得长期信息），游戏流程不中断。
7. **Given** 玩家多次提及某话题但从未成为具体事件（如反复聊起"妹妹"），**When** 后续对话中该话题再次出现，**Then** NPC 表现出模糊印象（"你好像提起过……"级别的态度，而非引用具体事实），印象不张冠李戴、不编造细节；注入按权重阈值（近期必记 + 提及次数衰减 + 在意值缩放）而非硬次数门槛。

> **实现补记（2026-09-21）**：记忆体系实际落地为**四级存储**——短期窗口 / 经历摘要 / 长期档案 / **模糊印象层**（`app/services/memory/topics.py`，双通道注入 + 权重衰减，e6cb948/fed9cf8 迭代）。印象防张冠李戴与对话防复读已由 `tests/services/test_memory_topics.py` 覆盖。
>
> **实测三修（2026-09-21，真实对话复盘）**：拿真实会话记录（45 轮）对照后发现三个问题并修复——
> 1. **幻视/编造过去**：prompt 里「不得凭空断言过去事件」的约束原先被包在 `if history:` 里，**会话第一轮根本不生效**，于是首轮就出现「上次的烤鱼」这类无据断言。已移到常驻约束并加强（模糊印象只有话题、不含事实），由 `test_memory_honesty_rule_present_even_without_history_or_memories` 钉住。
> 2. **印象自我强化回路**：她自己的回复也提取主题入印象（设计如此），但走的是**与玩家同一条强化路径**——「注入 → 她提起 → 计数 +1 → 更必注入」形成正反馈，实测「钓鱼」被计到 24 次、印象层塞满 200 条。现在 `origin=companion` 的提及**不加深、不刷新时间**（仅首次留痕，表示"她记得自己说过"），玩家提及仍可升级来源并正常强化；检索端对近期会话已聊过的话题**本轮冷却不注入**。
> 3. **停用词噪声入印象**：实测落进印象层的「不过 / 这话 / 人机味 / 幻视」等碎片会被当成"对玩家的印象"注入，让角色说怪话。黑名单扩充（幻视/幻觉/人机/人机味）+ 噪声表扩充（指代/领属词）。历史数据不会自愈，新增一次性清洗脚本 `scripts/prune_noise_impressions.py`（支持 `--dry-run`，已清洗现有 14 条）。
>
> **残留待办**：① 规则提取仍会产出「以为 / 前面 / 这么定」这类无法穷举的碎片（正式路径走 LLM 顺带返回，规则仅为降级）；② 旧数据里被正反馈抬高的话题（钓鱼 n=24）靠半衰期自然淡出，可另用清洗脚本重置。
>
> **四补：让「有据可说」成为默认路径（2026-09-21）**。三修之后复盘根因：`short_term / summaries / archive` 三层在真实运行中**恒为空**（`record_experience` 只有测试和 demo 在调），长期信息全靠印象层承载——而印象只有话题、没有事实。她手里没有任何可引用的事实，遇到「上次的烤鱼」这种问法只能脑补，这正是幻视的土壤。本轮把另两层接上：
> - **事实通道**：LLM 顺带返回 `facts`（0~3 条关于玩家本人的、跨会话仍成立的第三人称陈述），落**档案层**（`MemoryStore.record_facts`，按内容去重、重复提及只刷新时效不新增、不降级重要性）。注入端 `format_memory_block` 按来源分口吻（"the player told you" / "you two went through together" / "the player promised you"），并明确许可「这些可以直说，但不得加细节」——否则她连记得的事也会含糊其辞。
> - **接地校验**（`app/services/memory/facts.py`）：档案里的事实会以「她确定知道」长期注入，**编造一条就是永久错误记忆，比当场幻视严重得多**。因此写档前做轻量接地校验——事实的实词（剥离「玩家」前缀与高频功能字后的字符集）至少一半要能在玩家真说过的话（本轮 + 近期会话）里找到，对不上直接丢弃（印象层仍留痕）。宁可漏掉一条真事实，也不让编造进档案。
> - **共同经历通道**：`/v1/world/events`（含 v0.2 战斗通道）处理成功后，把有共同经历语义的事件（第一次踏进某地 / 收到礼物 / 玩家替她挡刀 / 承诺兑现 / 击败强敌）写进**摘要层**；瞬时战斗状态（血量告急、蓝量过低）不入记忆——那是当下要处理的情况，不是回忆。细节只取上报方给过的 `details` / 快照字段，取不到就写泛一点，绝不推断；重放事件不重复记（幂等检查之后才写 + 摘要层按内容去重兜底）。
>
> 测试 605 通过（新增 22：接地校验、档案去重、事实落档/拦截/注入、共同经历模板与幂等重放）。
>
> **五修：情绪惯性 + 按字面理解玩家（2026-09-22，同一份 45 轮复盘续修）**：
> - **情绪惯性**：此前每轮独立生成，prompt 里没有「她现在什么心情」，模型只能按剧情张力重挑一个——实测出现无来由的情绪跳变与回摆。`DialogueTurn` 新增 `emotion_id` 作为惯性载体（`session_memory.record` 接收、`_record_turn` 传 `response.emotion_id`），prompt 注入 `Your current mood: <上一轮情绪>` 并要求「除非玩家的消息真的改变了处境，否则保持这个心情」。**同时收回上一版 Anti-repetition 里「emotion_id 也要轮换」的指令**——那条正是情绪抽签的来源（手势/表情仍要求轮换，句法/长度/节奏仍不得复读）。mock/回退路径同样有 `emotion_id`，降级时心情照常延续。
> - **按字面理解玩家**：实测连续四轮把普通提问/陈述事实读成挑衅，并给玩家安上「嘴硬」「硬撑」「不肯靠过来」这些他没表达过的态度——敌意归因比记错事更伤体验。`conversation_rules.response_rules` 新增 4 条：按字面理解（不得读成挑衅/较劲/嘴硬，不得指责逞强找借口）、不得安上玩家未表达过的态度动机、打趣只在玩家起头或情境轻松时用且不得连续两轮带刺、大部分回复应是平常温和语气（俏皮是调味不是主菜）。
> - `runtime_state_policy` 同步改为「同一窗口内延续上一轮情绪」+「关系数值与阶段、四级长期记忆为跨会话状态」，与已落地的 US1/US2 对齐（原文仍写着「不维护当前心情、长期摘要」）。

> **六修：止住幻觉源头 + 能力有据可依 + 印象噪声走 LLM 通道（2026-09-22，魔法对话约 30 轮复盘）**：
> - **few-shot 在教她编造记忆（分量最重的根因）**：5 条 `memory_recall` 示范全部是「自信说出玩家从没说过的事」（你怕高/旧王国桥边/看海/蘑菇/热汤面），与 Memory honesty 正面冲突且 few-shot 权重更高——实测「当然记得，才几天不见」即此模式翻版。全部重写为「有据直说、无据不确定/反问」+ 一条正向示范（玩家当场说过 → 如实引用）。「prompt 指令静默打架」最重的一例：示例与规则文字不同向时，模型学的是示例。
> - **示例被当事实源**：天气示范「云层压得有点低，多半要下雨」被逐字复述成真实天象（请求无 world_context）。天气条改为「说不准」示范；prompt 示例块加框定「世界细节是占位不是事实」。

> - **honesty 扩面**：从「过去事件」一类扩到四类（+世界状态/自身能力/相处时长），实测三类现编都发生在旧覆盖之外。
> - **自述主题走 LLM**：她自己的回复此前走规则切词（无分词库），碎片「主修/厉害/水系本来」直接落印象且新印象立即回注。`_DialoguePayload` 新增 `reply_topics`，LLM 路径绕开规则切词；噪声表扩入实测碎片，存量清洗 6 条。
> - **response_rules 补两条**：玩家打趣不当真（实测「那你很弱欸」被当真较劲）；先接住玩家本轮内容、指令式叮嘱不连用（实测「跟紧点」两轮重复）。

#### User Story 2 - 关系会变化，并真的改变她的行为 (Priority: P1)

NPC 与玩家的关系是一段会成长的关系。玩家保护她、认真对待她、送她东西，会让她更亲近；玩家无视她的警告、反复让她受伤、长时间冷落，会让她疏远。关系的不同阶段，NPC 不只是"语气变了"，而是**行为也变了**：疏远时优先自保、保留资源；亲近时愿意为玩家消耗珍贵能力、主动搭话，甚至在玩家下达明显送死的命令时提出反对。

**Why this priority**: 关系数值若只影响台词，就是装饰而非系统。本故事要求关系真实渗透进决策，是"人格"可被感知的关键。

**Independent Test**: 用同一句指令（如"帮我回一下血"）分别在关系疏远与亲近两种状态下触发，对比 NPC 的语气、称呼、资源投入意愿与服从度差异。可独立于非战斗内容演示。

**Acceptance Scenarios**:

1. **Given** 玩家在关系初期提出请求，**When** NPC 需要消耗珍贵资源，**Then** NPC 表现出审慎与保留，并明确说明理由。
2. **Given** 玩家与 NPC 已建立深厚关系，**When** 玩家处于危机并请求支援，**Then** NPC 愿意投入高成本能力，且语气与称呼明显更亲近。
3. **Given** 玩家下达一个明显会导致 NPC 或玩家死亡的命令，**When** NPC 关系处于亲密阶段，**Then** NPC 有权以角色口吻提出反对或给出替代方案，而非无条件执行。
4. **Given** 玩家在短时间内重复同一行为（如反复赠送），**When** 该行为累计超出单位时间的合理上限，**Then** 关系数值不再提升，避免刷分。
5. **Given** NPC 关系已到达上限或下限，**When** 继续发生正向或负向事件，**Then** 数值保持在边界内不越界。
6. **Given** 关系状态数据损坏或缺失，**When** 玩家继续游戏，**Then** 系统以初始关系继续运行，不出现错误或卡死。

> **实现补记（续）：对话推动关系（2026-09-22）**。原 US2 设计只覆盖事实事件驱动；实测（约 45 轮真诚交流后仍是 distant(20)）暴露对话链路纯只读——而对话才是陪伴玩法的主体。新增能力：LLM 顺带返回 `relationship_signal`（none/warm/deep/cold/hurtful，判玩家发言的情感质量，绝大多数轮次为 none——宁漏勿滥），映射 4 类 `dialogue_*` 事件走 `RelationshipStore.apply_event` 唯一入口，冷却/日上限/持久化全套复用。校准（用户拍板「半天~一天一档」）：warm +1 / deep +2 / cold -1 / hurtful -2，distant→neutral 约 3~5 轮真诚交流；对话专属冷却 300 秒（对话每轮都发生，比事实事件 60 秒严）；每日正向上限与事实事件共享、负向不限（疏远不需要配额）。响应新增 `relationship_delta`（附加式扩展）；阶段变化自下一轮生效，下游（称呼/语气/硬边界/战术调制/自主行为门槛/记忆在意值）自动跟随。mock 路径不推动关系（规则判不了情感质量）。验收场景 4 的防刷语义对对话信号同样成立（冷却窗口测试覆盖）。

#### User Story 3 - 她在没有战斗的时候也活着 (Priority: P1)

在探索、营地休整与待机时，NPC 会做自己的事并主动与玩家互动：靠近值得注意的东西看一眼、发现线索时提醒玩家、下雨时找遮蔽、入夜时提议休息、闲下来时会自言自语或主动搭话。她的这些行为是**由系统判断后发起的**，不需要玩家每次下命令，也不会打扰正在进行的剧情演出。

**Why this priority**: 项目要求"负责整个 NPC 的活动塑造"。若 NPC 只在战斗中工作，本项目的定位升级就落空了。

**Independent Test**: 让玩家在非战斗场景中静止一段时间，观察 NPC 是否基于环境（附近的物件、时间、天气）产生合理且不重复的自主行为；可由单人演示，不需要战斗系统。

**Acceptance Scenarios**:

1. **Given** NPC 处于探索状态且附近出现值得关注的对象，**When** 系统收到世界状态更新，**Then** NPC 产生一次与之相关的行为（观察、查看、提醒），且该对象在短期内不重复触发。
2. **Given** 游戏时间进入夜晚，**When** 系统收到时间更新，**Then** NPC 提出与作息相关的行为或建议（如提议休息），若该能力被配置关闭则保持静默。
3. **Given** 玩家正在观看关键剧情演出，**When** 系统判断当前不宜打断，**Then** NPC **不**发起任何自主行为。
4. **Given** 系统短时间内收到了大量世界状态更新，**When** 自主行为触发条件成立，**Then** 系统按节流规则限制频率，避免刷屏。
5. **Given** 玩家刚刚对 NPC 下达了指令，**When** 同一时刻存在自主行为候选，**Then** 玩家指令优先，自主行为让位。
6. **Given** 游戏进入战斗状态，**When** 系统收到世界状态更新，**Then** 只产生战斗相关行为，不产生生活类自主行为。

#### User Story 4 - 战斗中我可以用自然语言指挥她 (Priority: P1)

玩家以文字或语音下达战术意图（"等它晕了就放大招""帮我回血""先撤"），NPC 根据当前战况给出**不同且可解释**的选择。同一句"帮我回血"，在玩家濒危、Boss 狂暴、NPC 蓝量不足等不同情境下，会有不同的应对与说明，而不是机械执行同一个动作。

**Why this priority**: 这是项目既有的核心亮点与答辩主线，定位升级后必须保留并继续可用。

**Independent Test**: 用同一句指令配合多组不同战况输入，验证输出随情境变化且每一条变化都能说明理由。

**Acceptance Scenarios**:

1. **Given** 玩家在语音或文本中表达同一战术意图，**When** 当前战况不同（玩家濒危 / 玩家健康 / 目标处于破绽状态 / NPC 资源不足），**Then** NPC 给出不同但合理的选择，并说明依据。
2. **Given** 玩家提出的技能或目标不在当前可用范围内，**When** NPC 无法执行，**Then** 明确告知原因或给出替代建议，**不**擅自替换成别的能力。
3. **Given** 玩家指令含糊或无法识别，**When** 系统无法确定意图，**Then** NPC 以角色口吻请求澄清，**不**猜测执行。
4. **Given** 玩家下达需要等待时机的指令（如"等它露出破绽再打"），**When** 时机尚未到来，**Then** NPC 记下该指令并在条件满足时执行一次，不重复执行。
5. **Given** 玩家用语音下达指令，**When** 语音服务不可用，**Then** 玩家得到明确反馈且战斗流程不受影响。
6. **Given** 模型服务不可用，**When** 玩家下达已被规则覆盖的常见指令，**Then** 指令仍能被正确执行（服务降级，不失效）。

#### User Story 5 - 世界发生事情时她有反应，且不会重复反应 (Priority: P2)

当世界状态发生有意义的变化（玩家血量骤降、目标进入破绽、玩家发现新区域、天气突变、玩家赠礼），NPC 会在恰当时机给出一次反应（台词、表情、动作或建议）。同一次事件因网络重试被重复上报时，NPC **不会**重复说话或重复行动。

**Why this priority**: 主动反应让 NPC 从"应答机"变成"同伴"；幂等保证演示时不会出现"复读"这类明显的体验事故。

**Independent Test**: 上报一次事件并观察反应，随后以相同事件标识重试上报，验证第二次仅回放首次结果且不产生新行为。

**Acceptance Scenarios**:

1. **Given** 玩家血量首次跌破危险线，**When** 系统收到该事件，**Then** NPC 只主动关切一次，若玩家恢复到安全线以上再次跌破，则可再次触发。
2. **Given** 目标进入破绽状态，**When** 系统收到该事件，**Then** NPC 给出集火提示，并在条件允许时提出行动建议。
3. **Given** 同一事件被重复上报（网络重试），**When** 系统再次处理，**Then** 返回与首次一致的结果并标记为重复，**不**产生新的行为。
4. **Given** 事件要求的行动当前不可用（资源不足、技能冷却），**When** 系统处理该事件，**Then** 不虚构动作，仍返回台词与建议。
5. **Given** 玩家首次进入一个新区域，**When** 系统收到该事件，**Then** NPC 给出一次与该区域相关的反应，同一区域短期内不重复触发。

#### User Story 6 - 她回答设定问题时以事实为准，而不是编 (Priority: P2)

当玩家询问世界观设定、当前战况或环境信息（"这个遗迹是谁建的""我们现在有多少胜算""那边那个东西是什么"），NPC 会先查证再回答。查不到就坦白不确定，而不是编一个听起来合理的答案。

**Why this priority**: 一个会编造世界观的 NPC 会直接损害作品可信度；这也是本项目"Agent 化"的体现。

**Independent Test**: 分别提问有据可查与无据可查的问题，验证前者与事实一致、后者明确表示不确定。

**Acceptance Scenarios**:

1. **Given** 玩家询问一个已知设定，**When** NPC 回答，**Then** 回答内容与设定库一致，不新增未经记录的事实。
2. **Given** 玩家询问一个设定库中没有答案的问题，**When** NPC 回答，**Then** 明确表示不确定或以角色口吻表示"需要再查证"，**不**编造具体事实。
3. **Given** 玩家询问当前战况，**When** NPC 回答，**Then** 内容与最新收到的世界状态一致，不使用过时状态。
4. **Given** 查证过程耗时或失败，**When** 超出可接受等待时间，**Then** 系统放弃查证直接给出回应，玩家不会长时间无响应。
5. **Given** 玩家询问的内容涉及不应披露的内部信息，**When** NPC 回答，**Then** 拒绝披露且不泄露任何内部细节。

#### User Story 7 - 我能看见她为什么这么做 (Priority: P2)

在演示与调试时，玩家/评审能看到完整决策链路：输入了什么、识别出什么意图、当前关系处于哪个阶段、最终做了什么决定、依据是什么、执行结果如何。NPC 的每个行为都能被解释，而不是"模型黑箱"。

**Why this priority**: 项目以"可解释"为核心卖点之一，也是答辩能否讲清楚的关键。

**Independent Test**: 触发一次指令，检查链路信息是否完整覆盖"输入→理解→关系状态→决策→依据→结果"。

**Acceptance Scenarios**:

1. **Given** 一次指令处理完成，**When** 查看链路信息，**Then** 可看到输入、识别结果、决策、依据说明与实际执行结果。
2. **Given** 系统发生降级（模型不可用、查证失败、存储异常），**When** 查看链路信息，**Then** 能明确看出降级发生在哪一环。
3. **Given** NPC 做出了一个与玩家预期不同的选择，**When** 查看依据，**Then** 能读到可理解的原因说明（而非仅一个错误码）。
4. **Given** 演示需要复盘某次交互，**When** 按交互标识检索，**Then** 能定位到该次交互的完整记录。

#### User Story 8 - 以后加第二个 NPC 不需要重写系统 (Priority: P3)

项目当前只需一个 NPC，但要求体系支持扩展：未来增加新角色时，只需新增其人格与能力配置，无需改动系统结构。不同 NPC 的记忆与关系互不干扰。

**Why this priority**: 属架构目标，不阻塞当前演示，但决定"人格体系"是否具备通用性。

**Independent Test**: 在不变更系统结构的前提下接入第二个角色的配置，验证其可被正确识别与独立运行。

**Acceptance Scenarios**:

1. **Given** 存在一个新的角色配置，**When** 系统被请求处理该角色，**Then** 正确路由到该角色的人格与能力，不使用他人人格。
2. **Given** 两个角色同时使用，**When** 分别进行对话与交互，**Then** 各自的记忆与关系互不影响。
3. **Given** 请求了一个未登记的角色，**When** 系统处理，**Then** 明确拒绝，**不**回退使用默认角色的人格。
4. **Given** 某个角色的配置损坏，**When** 系统运行，**Then** 仅该角色不可用，其他角色与整体服务不受影响。

#### Edge Cases

- 玩家在同一句话中表达多个相互冲突的意图时，如何处理（例如"别放大招了，快撤"）？
- 玩家在战斗与非战斗状态切换的瞬间下达指令，归属哪个场景？
- 关系数值恰好处于两个阶段的边界时，以哪一阶段的表现呈现？
- 记忆内容容量已满且新出现的经历重要性同样较低时，淘汰依据是什么？
- 上传的语音为空、过短、或只有环境噪声时，如何反馈？
- 玩家在两台设备／两个存档间切换时，记忆与关系如何处理？
- 系统时钟回拨或游戏内时间跳变（读档、快进）时，与时间相关的行为与衰减如何处理？
- 玩家在演出期间强行输入指令，如何在不破坏演出的前提下响应？
- 网络重试与真实重复事件（短时间内确实发生两次同类事件）如何区分？
- 模型输出包含违规表达或出戏内容时，重试仍失败的下限行为是什么？

### Requirements *(mandatory)*

#### Functional Requirements

**人格与表达**

- **FR-001**: 系统 MUST 以单一配置源定义每个 NPC 的人格（身份、背景、价值观、好恶、说话风格、禁忌表达、语气示例），且人格文案不得散落在代码逻辑中。
- **FR-002**: 系统 MUST 保证 NPC 的表达在其人格设定范围内，且**禁止**出现游戏机制、系统、协议等破坏沉浸感的术语。
- **FR-003**: 系统 MUST 对所有 NPC 输出执行内容校验，拒绝符合禁忌表达清单的内容；校验失败时 MUST 重试并以角色化表达兜底。
- **FR-004**: 系统 MUST 支持NPC 的持续情绪状态与当前关注点，使其跨多次交互保持情绪连贯（而非每次重置）。
- **FR-005**: NPC 人格中的核心设定 MUST 不可被模型输出或玩家输入改写。

**记忆**

- **FR-006**: 系统 MUST 持久化 NPC 的记忆，使其在重启后仍然有效。
- **FR-007**: 系统 MUST 分级管理记忆：当前会话内的短期上下文、跨会话的经历摘要、长期关系与事实档案，并明确各自的容量与淘汰规则。
- **FR-008**: 系统 MUST 在记忆达到容量上限时按重要性与时间淘汰，且承诺类与重大事件类记忆 MUST 优先保留。
- **FR-009**: 系统 MUST 在生成回应时按可控预算使用记忆，避免上下文无限增长。
- **FR-010**: 系统 MUST 提供清空指定 NPC 记忆的能力。
- **FR-011**: 记忆不可用时，系统 MUST 继续提供服务并降级为无长期记忆的行为，且 MUST NOT 因此中断玩家流程。
- **FR-012**: 系统 MUST NOT 将推测内容作为事实写入长期记忆，且记忆条目 MUST 可追溯来源与发生时间。

**关系**

- **FR-013**: 系统 MUST 为每个 NPC 维护对玩家的长期关系状态，并持久化。
- **FR-014**: 关系变化 MUST 由游戏内发生的**事实事件**驱动，且事件类型与影响幅度 MUST 可配置。
- **FR-015**: 系统 MUST 对同类事件的重复触发实施限制，防止通过重复行为快速刷高关系。
- **FR-016**: 关系状态 MUST 划分阶段，且每个阶段 MUST 定义可观察的差异，至少覆盖：称呼与语气、主动互动频率、资源投入意愿、对危险指令的服从度。
- **FR-017**: 关系 MUST NOT 导致违反安全与合规约束的行为，也 MUST NOT 使 NPC 越过玩家边界或出现控制性表达。
- **FR-018**: 关系状态异常时，系统 MUST 以初始状态继续运行。

**活动与自主行为**

- **FR-019**: 系统 MUST 区分 NPC 所处的活动场景（战斗、探索、营地休整、对话、待机），并在不同场景下提供不同的可执行行为集合。
- **FR-020**: 系统 MUST 支持 NPC 在非战斗场景中的自主行为，且自主行为类型 MUST 覆盖不少于 8 类（含跟随、移动、观察、查看、交互、拾取、休整、等待、表达、自言自语等）。
- **FR-021**: 系统 MUST 在无玩家指令时，基于客户端上报的世界状态与世界时间判断是否发起自主行为；系统 MUST NOT 主动向客户端推送。
- **FR-022**: 系统 MUST 对自主行为实施节流与去重，保证同一触发源在短期内不重复触发，并限制单位时间内的触发次数。
- **FR-023**: 系统 MUST 支持禁止打断的情形（剧情演出、玩家正在说话、NPC 正在施法、界面弹窗），在这些情形下 MUST 不发起自主行为。
- **FR-024**: 系统 MUST 按统一优先级仲裁多个候选行为，优先级从高到低 MUST 至少覆盖：危险自保、战斗战术、玩家指令、剧情事件、关系事件、日常自主行为。
- **FR-025**: 系统 MUST NOT 输出无法执行的行为；当目标、条件或资源不满足时，MUST 返回明确的不可执行说明而非虚构行为。

**指挥与决策**

- **FR-026**: 系统 MUST 支持玩家以文本与语音两种方式下达指令，语音在转写后 MUST 进入与文本一致的后续处理。
- **FR-027**: 系统 MUST 将玩家自然语言解析为受白名单约束的语义意图，且解析 MUST 在规则与模型两种方式间可切换并在失败时自动降级。
- **FR-028**: 系统 MUST 在解析无法确定意图时请求澄清，MUST NOT 猜测执行。
- **FR-029**: 系统 MUST 结合当前世界状态、NPC 自身状态与关系阶段决定最终行为，并保证同一意图在不同情境下可产生不同结果。
- **FR-030**: 系统 MUST NOT 使用当前不可用的能力，也 MUST NOT 以目录外的能力替代玩家的指定目标。
- **FR-031**: 系统 MUST 为每次决策产出可解释的原因说明。

**事件与世界反馈**

- **FR-032**: 系统 MUST 处理客户端上报的世界事件（含战斗与生活两类），并返回 NPC 的反应与可选建议。
- **FR-033**: 系统 MUST 对事件处理实施幂等，同一事件标识重复上报时 MUST 回放首次结果且不产生新行为。
- **FR-034**: 系统 MUST 仅依据世界状态边沿变化触发反应，MUST NOT 依赖逐帧上报。

**能力与工具**

- **FR-035**: 系统 MUST 以统一注册表描述 NPC 的全部可用能力，涵盖战斗行为、生活行为与信息查询三类。
- **FR-036**: 系统 MUST 允许为回答设定类与状态类问题而查证权威信息源，且查证 MUST 为只读。
- **FR-037**: 查证失败或无结果时，系统 MUST 明确表示不确定，MUST NOT 编造事实。
- **FR-038**: 查证 MUST 有轮次与时间上限，超限后 MUST 降级为直接回应。

**安全与边界**

- **FR-039**: 系统 MUST NOT 直接改变游戏世界状态；一切改变 MUST 以受约束的指令形式交由客户端执行，客户端 MUST 保有最终否决权。
- **FR-040**: 系统下发的指令 MUST 只引用本次交互上下文中已存在的标识，越界 MUST 被拒绝。
- **FR-041**: 系统 MUST 在任一子系统（模型、语音、记忆、关系、查证、配置）故障时保持可用并降级，MUST NOT 阻塞客户端的游戏主流程。
- **FR-042**: 系统 MUST 记录每次交互的来源与版本信息，用于观测与归因，且 MUST NOT 将交互数据自动用于训练。
- **FR-043**: 系统 MUST NOT 在输出中泄露内部实现细节（路径、资产名、坐标、函数名、凭据）。
- **FR-044**: 系统 MUST 支持面向多个 NPC 的路由与状态隔离，且未登记角色 MUST 被拒绝而不回退至默认角色。

**架构约束**

- **FR-045**: 系统 MUST 采用**单一指令体系**：所有下发指令使用同一信封并按行为类型区分；实现层按活动场景分文件组织，MUST NOT 建立平行的多套指令体系。

#### Key Entities

- **NPC 人格档案**：描述一个角色的身份、背景、价值观、好恶、说话风格、禁忌表达与示例语料；是角色的唯一人格来源，可被多个运行实例复用。
- **记忆条目**：一条可持久化的经历记录，含内容、重要程度、发生时间（游戏内与真实时间）、来源与标签；多条聚合为角色的经历摘要与长期档案。
- **长期关系档案**：记录某 NPC 对某玩家的关系数值、当前阶段、重要事实、承诺与禁忌话题。
- **世界状态快照**：客户端某一时刻观测到的事实集合，含活动场景、世界时间与天气、区域、玩家状态、NPC 状态、周围可交互对象；是只读的输入，不承担权威状态职责。
- **行为指令**：系统下发给客户端的受限行为请求，含唯一标识、目标角色、所属场景、行为内容、优先级、有效期、来源与依据说明。
- **世界事件**：客户端在状态边沿上报的一次有意义变化，含唯一标识、类型、发生时间与序号；处理结果可被幂等回放。
- **能力与工具**：NPC 可执行的行为单元与可调用的只读信息源，统一登记适用场景、参数与前置条件。
- **执行回执**：客户端对指令处理结果的反馈，含指令标识、结果状态与原因；仅用于观测与评测，不反向改变游戏事实。

### Success Criteria *(mandatory)*

#### Measurable Outcomes

- **SC-001**: 玩家在会话中提及的个人信息与共同经历，在服务重启后再次对话时能被正确引用，正确率 **100%**（抽样不少于 20 条记忆）。
- **SC-002**: 同一句战术指令在不少于 4 类不同战况下产生不同且合理的结果，人工判定合理率 **≥ 90%**。
- **SC-003**: 关系状态在不少于 3 个阶段下，同一指令的语气与行为表现可被人工区分，区分成立率 **≥ 90%**。
- **SC-004**: 在单位时间窗口内重复触发同类关系事件，关系数值变化为 **0**（防刷有效）。
- **SC-005**: 非战斗场景中 NPC 可观察到的自主行为类型 **≥ 8 类**，且每类至少可稳定复现一次。
- **SC-006**: 自主行为的重复触发率（同一触发源在窗口内重复）为 **0**；打断关键演出的次数为 **0**。
- **SC-007**: 同一事件重复上报时，重复响应率（产生第二次实际行为）为 **0**。
- **SC-008**: 设定类问题的回答与权威信息源一致率 **100%**；无据可查时明确表示不确定的比例 **100%**（不允许编造）。
- **SC-009**: 指令中引用的能力或目标超出当前可用范围的越界下发次数为 **0**。
- **SC-010**: 任一子系统故障时，玩家可继续正常游戏且能得到可理解的反馈，流程中断次数 **0**。
- **SC-011**: 战斗场景下从玩家发出指令到 NPC 开始响应的等待时间，玩家可感知为"即时"，人工评估达标率 **≥ 95%**。
- **SC-012**: 新增第二个角色时，系统结构无需变更即可正确路由并隔离状态，验收通过率 **100%**。
- **SC-013**: 演示时，评审可对任意一次 NPC 决策获得"输入—理解—关系状态—决策—依据—结果"的完整解释，覆盖率 **100%**。

### Assumptions

- 目标用户为**单人本地玩家**，不存在多用户并发、账号体系与联网对战需求。
- 客户端（游戏端）具备采集世界状态、执行行为指令、播放表现的能力，并遵守"客户端为权威端"的边界约定。
- 客户端能够按约定提供世界时间与区域信息；缺少这些信息时，与时间/区域相关的自主行为不启用。
- 模型服务与语音服务为可选依赖：不可用时系统以规则方式继续提供核心能力，属可接受降级。
- 运行环境为开发者本机，硬件资源有限（不能同时运行重型模型任务），因此不引入重型中间件。
- 记忆与关系数据属于**本地存档性质**，不要求跨设备同步；玩家可在本地重置。
- 角色的核心人格由人类作者定义，系统**不允许**角色自行演化人格或改写核心设定。
- 关系数值的**事实来源**由客户端上报，数值计算与存储由服务负责。
- 本项目为课程项目，交付范围以"可演示、可解释、可验收"为准，不追求生产级并发与运维能力。
- 角色属于虚构游戏角色，不存在真实人物映射；内容表达遵守通用合规要求（无不当与侵害性内容）。

## Implementation Plan: Aesir NPC 人格与行为代理系统

**Branch**: `001-aesir-npc-agent` | **Date**: 2026-09-13 | **Spec**: spec.md

**Input**: Feature specification from `specs/001-aesir-npc-agent/spec.md`

### Summary

把现有「语音 → 战术命令」服务升级为「NPC 人格与行为代理」：在保留既有战斗指挥能力的前提下，
新增**持久化记忆**、**关系状态（好感度）**、**非战斗活动域与自主行为**、**只读查证工具**，
并把下发命令统一到**单一指令体系**（统一信封 + 按类型判别，实现按活动域分文件）。
UE 仍为唯一权威端，服务只输出受限指令。

技术路线：沿用现有 FastAPI + Pydantic v2 服务骨架，把新增能力做成**并列的服务模块**，
通过一个统一入口编排；所有规则、阈值、文案外置配置；持久化采用本地文件（不引入数据库）。

### Technical Context

**Language/Version**: Python 3.12（现有工程基线 3.12.7）

**Primary Dependencies**: FastAPI、Uvicorn、Pydantic v2、pydantic-settings、httpx、PyYAML、python-multipart；可选 faster-whisper（语音）、gymnasium/stable-baselines3（可选 RL 旁路）

**Storage**: 本地文件（JSON／JSONL）；记忆与关系落 `data/memory/<npc_id>/`，回执落 `data/rl/executions/`；**不引入数据库、缓存或消息队列**

**Testing**: pytest + FastAPI TestClient；测试隔离外部后端（规则／模拟后端），真实模型调用单独门控

**Target Platform**: Windows 11 开发机，本机回环部署；Python 代码保持跨平台可运行

**Project Type**: 单机 Web 服务（供游戏客户端调用），无前端

**Performance Goals**: 战斗指令端到端 P95 < 3s；非战斗自主行为判定 P95 < 1s（无产出时 < 100ms）；纯规则链路 P95 < 100ms

**Constraints**: 8GB VRAM（语音模型与可选训练不同时驻留）；无外网时须能完整运行规则链路；禁止绑定非回环地址

**Scale/Scope**: 单玩家、单客户端；架构支持多 NPC，首版启用 1 个；预计新增 12～16 个模块文件、40～60 条新测试
