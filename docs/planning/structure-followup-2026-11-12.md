## 3. 再检查后，项目结构还存在什么问题

### 3.1 `scoped.py` 仍是大型协调入口

当前约 685 行，包含控制绑定、文本/语音、事件、回执和恢复。它已经不再调用旧 HTTP 模块，但职责仍多。下一步可按控制、实时业务、查询/恢复拆 router，保留同一 `/v1/scoped` 前缀和共享执行门禁，避免复制 `_execute`、权限与绑定检查。

本轮没有为了压缩文件行数就把事务门禁散到多个地方。拆分应以接口和行为不变为前提，单独验收。

### 3.2 Agent 的业务本身仍然复杂

`app/api/v1/agent.py` 从约 693 行变为 7 行；真实业务位于约 692 行的 `services/agency/agent_service.py`。这解决了“新版依赖旧路由”，但不是把业务复杂度消除了。后续可按心跳、自主行为、玩家意图及指令组装分拆，先保留一个统一应用服务入口。

### 3.3 状态、事务与身份之间仍有双向依赖

例如 scoped.identity 在需要时导入 persistence.auth，而 auth 又使用 scope/context；database/UoW、journal/runtime、memory/storage 之间也有惰性导入连接。这些关系当前有回归覆盖，不等于现在必然循环导入崩溃，但让单独理解和替换模块困难。

下一阶段可把作用域标识、错误和存储接口等无业务副作用的类型下沉，再通过应用装配选择实现。不要一次移动所有类或改事务边界；持久化和重置屏障属于高风险区域。

### 3.4 服务层仍带部分 HTTP 异常

本轮保留了原 `HTTPException` 行为，避免接口错误语义突变。因此 service 层仍依赖 FastAPI 的异常类型，还不是完全与传输无关的领域层。后续可逐步转为业务异常、由统一 API 适配器映射，必须保持现有 403/404/409/503 行为。

### 3.5 全局缓存及配置生命周期不够直观

配置 getter 每次读取环境，但人格、策略、会话、运行时单例等生命周期不同。修改配置不代表全模块即时更新。当前先按指南重启；若要做可重载配置，需要明确依赖重建和请求隔离机制，不能只加一个 reload 开关。

### 3.6 文档状态仍有历史与当前口径混杂

已经删去明确过时的三份草案，并更新主要入口。历史日志、跨仓本地路径和课程材料还存在陈旧引用，不能因另一仓未检出就删除。新人以接手导览为入口，字段以当前 schema/OpenAPI 为准，验收看有日期与环境的证据。

## 4. 当前仍有哪些缺陷或交付缺口

对话 RL 仅保留信号与离线评估工作，没有上线在线学习或人格自演化。它不应优先于当前文本、指令、语音和可靠性闭环。

## 5. 接下来怎么做：按这个顺序

1. **先审阅并提交本轮改动，再推送验证 CI。**重点看抽出的 service、Boss 共享加载器、对话完成提交和三份文档删除。源码与全部新文件要一起提交；只提交旧文件会缺模块。
2. **完成一个最小 UE 真实闭环。**先 mock + wait，再 follow，最后接现有真实能力。每条链路都要保留实际动作和回执证据，验证重复请求不会重复执行。
3. **恢复真实 LLM，再把 ASR 串进去。**先验证文本，再识别，再整链路；记录 source、原因码与耗时，先不扩大功能范围。
4. **做故障与恢复演练。**换局旧回调失效、重复提交、断网、服务重启、清记忆、超时、SQL 恢复分别检查；Boss 材料未到位时不编造成功验收。
5. **明确数据保留策略并完成正式部署验收。**配置检查通过只是起点，补权限、HTTPS、真实依赖、备份/回滚及容量。
6. **再继续结构拆分。**优先 scoped router 和 Agent 分发；对事务层采用小步变更。不要同时改业务协议、存储和文件结构。

你现在最需要的是可复现的端到端证据和当前阻塞的解除，不是继续增加更多抽象层或启动新的训练任务。
