# 文档维护规范

## 命名

- 长期文档使用 `_编号_主题_类型.md`，编号两位，主题使用英文小写和下划线。编号在目录内稳定，不因删除文件重排。
- 计划使用 plan，操作说明使用 guide，持续问题清单使用 issues，协议使用 contract，结构评审使用 review。
- README.md 保留为目录入口。图源、JSON、HTTP 样例、SQL 和代码文件沿用各自格式，不套用 Markdown 命名规则。
- 正文标题和说明使用中文。长期文档不以日期、提交号或会话轮次命名。

## 临时材料

临时报告放入被忽略的 data/runtime 任务目录，采用 `YYYY-MM-DD-topic.md`，例如 `2026-11-12-structure-review.md`。任务完成且有效结论已写入长期文档/Issue，或审阅明确结束后删除；未审阅材料不因等待时间自动删除。测试原始证据与报告分别管理，不随报告一起批量删除。

## 正文内容

文档保留业务结论、设计、接口、问题、处理计划和必要的验证证据。不写聊天经过、用户角色声明、工具权限申请、CLI 连接过程、抓取来源数量或操作流水。必要的版本、日期、测试环境仅放在协议版本说明或验证记录中。

## 协议更新

同一协议仅维护一份当前整合文档和一份 previous 归档。升级时先把仍有效的兼容内容整合进当前文档，再替换上一版归档；更早副本删除，通过 Git 历史追溯。不同职责的有效协议不是互相替代的版本；合并不得删除仍被客户端使用的字段或兼容约定。修改文件名时同步维护本地链接、锚点、导出清单和检查脚本。
